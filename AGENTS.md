# Project guidance

- Keep `src/network.rs` and `src/demo.rs` independent of Ratatui and Crossterm. The library owns data, validation and aggregate calculations; the binary owns interaction and rendering.
- This foundation is synthetic and USD-only. Amounts are integer cents (`u64`); aggregate sums use `u128`. Opening balances are input data, never reduced by loading or viewing payments.
- Rails describe shared services and explicit membership, not directed graph edges. Payments are unassigned instructions; validation does not promise a feasible route or sufficient liquidity.
- `demo_network()` must remain deterministic, including collection ordering. The fixture has 6 institutions, 4 rails, 12 payments, USD 1,000,000.00 opening liquidity and USD 225,001.50 payment volume.
- Rail IDs/display names are `RTP`/RTP, `FEDNOW`/FedNow, `ACH`/ACH and `FEDWIRE`/Fedwire, in that order. These names are recognizable U.S. vocabulary; membership/topology, fees and timing remain synthetic. The demo has all rails available, no transaction ceilings and no delivery deadlines. The demo leaves batch capacity unlimited; availability schedules and actual network rules are not modeled. FedNow deliberately reuses RTP's synthetic inputs; this does not claim real-world equivalence. Keep the Rails ID column wide enough for the seven-character `FEDWIRE` at 80 × 18.
- Detect dependency versions from `Cargo.toml` and `Cargo.lock`, then query Context7 before changing library API usage. Ratatui is pinned to 0.30.0; use its Crossterm re-export to avoid conflicting event types ([Crossterm Version and Re-export](https://github.com/ratatui/ratatui/blob/ratatui-v0.30.0/ratatui-crossterm/README.md)). With default features disabled, retain `layout-cache` ([Breaking changes](https://github.com/ratatui/ratatui/blob/ratatui-v0.30.0/BREAKING-CHANGES.md)).
- Run relevant tests between changes, make atomic checkpoint commits, and create a PR only when directed. Single-payment static routing belongs in the terminal-independent library; no settlement engine or external solver is used.
- `cargo run --locked -- --demo` is the supported launch. Keep help and argument validation before terminal initialization. The UI needs 80 x 18; TestBackend checks minimum-size rendering and selection-driven scrolling. Actual PTY checks must also verify exit status and terminal modes after q, Esc and Ctrl-C when lifecycle code changes.
- `try_init` installs a panic hook but can return after partial setup. Always attempt restoration after initialization or event-loop errors ([Terminal initialization and restoration](https://github.com/ratatui/ratatui/blob/ratatui-v0.30.0/src/init.rs)). The event loop blocks on input and redraws on resize; this static viewer needs no timer.
- `route_payment` validates the network and the supplied instruction, including external instructions absent from `network.payments`. Rails connect every pair of members bidirectionally. Every hop carries the same USD principal and incurs the rail's fixed fee and latency; opening balances remain descriptive, not spendable or reserved routing capacity.
- Routing minimizes total fee, then latency, hop count, and the lexical sequence of `(rail_id, sender, receiver)`. Exact simple-path search is sufficient because fees and latency are nonnegative. Do not prune equal-cost paths or keep only the cheapest prefix at an institution when a delivery deadline can matter. Worst-case search is exponential; this is a small-network reference.
- The single-payment constraint fields are `Rail.available`, `Rail.max_amount_cents` and `Payment.max_delivery_minutes`. A ceiling is positive and inclusive, applies to principal excluding fees on every hop, and is not aggregate throughput. A deadline is inclusive and sums all hop latencies; zero allows only zero-latency routes. `None` means unconstrained. All inputs remain USD; no FX or additional currency model is implied.
- Keep the bounded-walk dynamic-programming oracle in `tests/routing_oracle.rs` independent of production search helpers. It checks fee/latency/hop optima and route witnesses across small exhaustive networks; focused tests cover lexical ties and wide totals. Run `cargo run --locked --example route_one` for asserted, hand-calculated constraint counterexamples without terminal initialization.
- `Rail.batch_capacity_cents` is a separate synthetic principal budget for one optimization batch: every hop consumes its full payment amount from the same rail budget across all members and both directions, excluding fees. `None` is unlimited; `Some(0)` is valid and permits no batch use. Capacity never replenishes or nets within a batch. Institution opening balances stay descriptive. Single-payment routing deliberately ignores this batch-only field. Demo rails default to unlimited; TUI behavior is unchanged.
- `batch::optimize_batch` routes exactly the supplied batch, validates the entire network and all supplied instructions, and rejects duplicate batch payment IDs. It returns a full plan or infeasibility, never a partial allocation. Assignments are ordered by payment ID and usage by rail ID; ties minimize total fee, summed latency, total hops, then route-hop sequences in that payment order. Returned usage and totals use `u128`; no inputs or budgets are mutated.
- Batch search retains all feasible simple paths, then backtracks over joint assignments. Do not reduce candidates to each payment's cheapest route or cheapest prefix: the six-assignment oracle counterexample has greedy cost 11 cents versus optimum 4, and independent minima overuse capacity. The sum of cheapest remaining route fees is only an optimistic pruning bound; prune strictly greater fees to preserve ties. This bound made the unchanged 12-payment demo practical after prefix-only pruning exceeded a minute. Keep the test oracle independent: it materializes bounded walks and the Cartesian product, checking capacity on complete assignments rather than sharing production pruning.
- Run `cargo run --locked --example route_batch` for the asserted six-assignment and multihop greedy counterexamples. `tests/batch_oracle.rs` makes 6,342 deterministic full-rank comparisons against the independent bounded-walk/product oracle; the oracle intentionally includes cyclic witnesses, so its raw walk count can exceed the number of simple routes.
